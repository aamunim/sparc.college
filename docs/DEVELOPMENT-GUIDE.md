## ০. কাজের পদ্ধতি

1. **"শুরু করো" বললে তবেই কাজ শুরু হবে।** একবারে একটা ধাপ, একটা বিষয়।
2. **একটা ফেজ শেষ না হলে পরের ফেজ শুরু হবে না।** প্রতিটা ফেজ শেষে Git tag দেওয়া হবে।
3. চলমান ফেজের মাঝখানে নতুন আইডিয়া ঢোকানো হবে না। সেটা যাবে [`ideas-backlog.md`](./ideas-backlog.md)-এ (দেখুন §১৫)।
4. প্রতিটা ফেজের **প্রস্থান-শর্ত (exit criteria)** পূরণ হলে তবেই ফেজ শেষ ধরা হবে (§৮)।
5. প্রতিটা পরিবর্তন §১৩-এর Definition of Done মেনে হবে।

## ২. মূল দর্শন: ফিচার নয়, ইঞ্জিন

সাধারণ অ্যাপে প্রতিটা ফিচারের জন্য আলাদা টেবিল আর আলাদা স্ক্রিন বানানো হয়। ফলে নতুন আইডিয়া এলে ডেটাবেস, কোড আর পারমিশন সব জায়গায় হাত দিতে হয়।

SPARC-এ শুরুতেই কয়েকটা **সাধারণ ইঞ্জিন** বানানো হবে। পরের প্রতিটা মডিউল (গবেষণা, হিফজ, স্টাডি সার্কেল, ভবিষ্যতের আইডিয়া) মূলত এই ইঞ্জিনগুলোর **কনফিগারেশন** হবে।

### ২.১ ইঞ্জিন তালিকা

| ইঞ্জিন | কী করে | নতুন আইডিয়া এলে কী লাগবে |
|---|---|---|
| **১. পারমিশন** | ভূমিকা আর অনুমতি ডেটাবেসে ডেটা হিসেবে থাকে; কোডে `can('course.publish')` চেক হয়, `role === 'teacher'` নয় | নতুন ভূমিকা = শুধু ডেটা (সারি যোগ) |
| **২. ফিচার ফ্ল্যাগ** | প্রতিটা ফিচার চালু/বন্ধ: সবার জন্য, নির্দিষ্ট প্রতিষ্ঠানের জন্য, বা নির্দিষ্ট প্ল্যানের জন্য; kill switch | নতুন ফিচার বন্ধ রেখে বানানো, টেস্টের পর চালু |
| **৩. কনটেন্ট** | কোর্স → সেকশন → **content item** (`type` + `config` JSON + `config_version`) | নতুন কনটেন্ট টাইপ = নতুন রেন্ডারার + config স্কিমা রেজিস্টার |
| **৪. অ্যাক্সেস রুল** | কে কখন কোন কনটেন্ট দেখবে: শিক্ষক রিলিজ, ক্রমানুসারে (আগেরটা অনুমোদিত হলে), ট্রায়াল, তারিখ, পেমেন্ট | নতুন rule type = `can_access_item()`-এ একটা নতুন শাখা (SQL) + params স্কিমা। বাকি সব আগের মতো |
| **৫. জমা ও অনুমোদন** | সাধারণ `submission → review` ফ্লো (নম্বর, মন্তব্য, approved/revision) | হোমওয়ার্ক, হিফজ শুনানো, গাইডেড রিডিং, গবেষণার ধাপ — সব একই ইঞ্জিনে |
| **৬. গ্রুপ** | একটা সাধারণ `groups` টেবিল, `type` (class, batch, research, study_circle, hifz …) | নতুন ধরনের গ্রুপ = নতুন type |
| **৭. ইভেন্ট ও নোটিফিকেশন** | যা ঘটে তা ইভেন্ট হিসেবে লগ হয় (`lesson.viewed`, `submission.reviewed` …); টেমপ্লেট সেই ইভেন্ট শুনে push/অ্যালার্ম/SMS/ইন-অ্যাপ পাঠায় | নতুন রিপোর্ট বা নোটিফিকেশন = নতুন টেমপ্লেট বা কুয়েরি |
| **৮. প্রোডাক্ট ও পেমেন্ট** | বিক্রয়যোগ্য সবকিছু একটা `product` (course, package, subscription, book, workshop …); পেমেন্ট চ্যানেল প্লাগইনের মতো | নতুন কিছু বিক্রি = নতুন product type |
| **৯. সেটিংস** | সিস্টেম/প্রতিষ্ঠান/কোর্স/গ্রুপের সেটিংস JSON-এ, টাইপ ও ডিফল্টসহ | নতুন অপশন = নতুন সেটিং কী; migration লাগবে না |

**উদাহরণ:** পরে আইডিয়া এলো "শিক্ষার্থী ভয়েস নোটে প্রশ্ন করবে"। নতুন টেবিল লাগবে না: Q&A-তে `audio` অ্যাটাচমেন্ট যোগ হবে; স্টোরেজ আর জমা ইঞ্জিন আগে থেকেই আছে।

### ২.২ ইঞ্জিন নিয়ে বাস্তব নিয়ম (সংশোধিত)

1. **"কাঠামো আগে, ভেতর ধাপে ধাপে"।** প্রতিটা ইঞ্জিনের টেবিল আর interface শুরুতেই ঠিক হবে, কিন্তু ভেতরে শুধু ততটুকুই বানানো হবে যতটুকু চলমান ফেজে দরকার। যেমন ফেজ ৪-এ শুধু ৪টা rule type, ৫টা content type। এতে MVP দেরি হবে না।
2. **পারমিশন JWT-তে নয়।** JWT-তে (Custom Access Token Hook দিয়ে) থাকবে শুধু membership: কোন প্রতিষ্ঠানে কোন ভূমিকা। নির্দিষ্ট পারমিশন যাচাই হবে `has_permission()` দিয়ে (`stable`, `security definer`, index-যুক্ত টেবিল)। কারণ: ভূমিকা বদলালে বা কাউকে সরালে সাথে সাথে কার্যকর হবে, আর টোকেন বড় হবে না।
3. **অ্যাক্সেস রুল সবসময় সার্ভারে যাচাই হবে।** ক্লায়েন্টে শুধু UI-তে তালা দেখানো হয়। তালিকা দেখানোর গতির জন্য একটা `item_unlocks` টেবিল থাকবে, যা ইভেন্ট (রিলিজ, অনুমোদন, পেমেন্ট) থেকে আপডেট হবে; চূড়ান্ত যাচাই হবে `can_access_item()` দিয়ে।
4. **content item-এর `config` দুই জায়গায় যাচাই হবে:** ক্লায়েন্টে zod দিয়ে, ডেটাবেসে `pg_jsonschema` দিয়ে। `config_version` থাকবে, যাতে পুরনো আর নতুন config আলাদা করে চেনা যায় এবং migrate করা যায়।
5. **যা ইঞ্জিনে ধরে না, শুধু সেটার জন্যই আলাদা মডিউল-টেবিল।** (§৬.২-এর "মডিউল-নির্দিষ্ট" অংশ)

## ৩. মাল্টি-টেন্যান্সি ও দৃশ্যমানতা মডেল

রিকোয়ারমেন্ট অনুযায়ী: স্বতন্ত্র ব্যবহারকারী আছেন (প্রতিষ্ঠান ছাড়া), একজন অভিভাবকের সন্তান একাধিক স্কুলে পড়তে পারে, একজন শিক্ষক একাধিক প্রতিষ্ঠানে পড়াতে পারেন, আর কোর্স নির্মাতার কোর্স সব প্রতিষ্ঠানের মানুষ কিনতে পারে। তাই নিচের মডেল:

### ৩.১ টেবিলের দুই ধরন

| ধরন | উদাহরণ | `institution_id` |
|---|---|---|
| **গ্লোবাল** | `profiles`, `parent_child_links`, `push_tokens`, `features`, `permissions`, প্ল্যাটফর্মের `products` | নেই, বা nullable |
| **টেন্যান্ট** | groups, courses, enrollments, submissions, events, … বাকি প্রায় সব | **বাধ্যতামূলক** (not null) |

- একটা বিশেষ প্রতিষ্ঠান থাকবে: **"SPARC Platform"**। স্বতন্ত্র ব্যবহারকারীর কার্যকলাপ আর কোর্স নির্মাতাদের মার্কেটপ্লেস কোর্স এখানে থাকবে।
- একজন ব্যবহারকারী একাধিক প্রতিষ্ঠানের সদস্য হতে পারেন (`user_roles`-এ একাধিক সারি)। অ্যাপে **প্রতিষ্ঠান + ভূমিকা সুইচার** থাকবে।
- প্রতিটা টেবিল কোন ধরনের, তা migration ফাইলের মন্তব্যে আর `docs/schema.md`-এ লেখা থাকবে।

### ৩.২ ডেটা বিচ্ছিন্নতা
- এক প্রতিষ্ঠানের ডেটা অন্য প্রতিষ্ঠান কোনোভাবেই দেখতে পারবে না। এটা প্রয়োগ হবে **RLS দিয়ে, সার্ভার স্তরে।**
- প্রতিটা টেন্যান্ট টেবিলের জন্য pgTAP টেস্টে "স্কুল A থেকে স্কুল B-র ডেটা পড়া/লেখার চেষ্টা" কেস থাকবে।

### ৩.৩ "কে কার কার্যকলাপ দেখবে" (রিকোয়ারমেন্ট ৪.৩)
এটা ভূমিকার ওপর নয়, **সম্পর্কের** ওপর নির্ভর করে। `can_view_student(viewer, student, context)` এই নিয়মে চলবে:

| দর্শক | কী দেখতে পারবেন | কোন সম্পর্কের মাধ্যমে |
|---|---|---|
| শিক্ষার্থী নিজে | নিজের সবকিছু | — |
| অভিভাবক | সন্তানের সবকিছু (সব প্রতিষ্ঠানে) | অনুমোদিত `parent_child_links` |

| অন্য কেউ | কিছুই না | — |

- **D10 (ডিফল্ট):** শিক্ষার্থী নিজে মার্কেটপ্লেস থেকে কোর্স কিনলে তার স্কুলের শিক্ষক সেটা দেখবেন না; অভিভাবক আর কোর্স ইনস্ট্রাক্টর দেখবেন।
- **অপ্ট-ইন দৃশ্যমানতা:** রিডিং রেকর্ড আর অ্যানোটেশন (রিকোয়ারমেন্ট ৪.৮, ৪.৯) ডিফল্টভাবে private; ব্যবহারকারী চাইলে `group` বা `teacher` দৃশ্যমানতা দেবেন।

## ৬. ডেটাবেস: কাঠামো ও নিয়ম

### ৬.১ নিয়ম
1. **স্ট্যান্ডার্ড কলাম** প্রতিটা টেবিলে: `id uuid`, `created_at`, `updated_at`, `created_by`, `deleted_at` (সফট ডিলিট), `meta jsonb`; টেন্যান্ট টেবিলে `institution_id not null`।
2. **সব পরিবর্তন migration ফাইলে।** পুরনো migration কখনো এডিট হবে না।
3. **শুধু যোগ, সরাসরি ভাঙা নয় (expand → migrate → contract):** কলামের নাম বদলাতে হলে আগে নতুন কলাম, তারপর ডেটা কপি, কোড আপডেট, সবশেষে (পরের রিলিজে, পুরনো অ্যাপ ভার্সন বন্ধ হলে) পুরনো কলাম সরানো।
4. **Enum নয়;** lookup টেবিল বা `text + check`।
5. **RLS সব টেবিলে চালু।** নিয়ম থাকবে কয়েকটা হেল্পার ফাংশনে (`private` schema-তে): `has_permission()`, `is_member()`, `can_view_student()`, `can_access_item()`। নিয়ম বদলাতে হলে শুধু ফাংশন বদলাবে।
6. **RLS-এর গতি:** `(select auth.uid())` প্যাটার্ন; হেল্পার `stable` + `security definer`; `institution_id`, `user_id` আর সব foreign key-তে index।
7. **Constraint দিয়ে ভুল ডেটা ঠেকানো:** foreign key, unique, not null, check।
8. **টাকা সবসময় integer (পয়সা)।** সময় সবসময় `timestamptz`।
9. **TypeScript টাইপ অটো-জেনারেট** (`supabase gen types`) — CI-তে মিলিয়ে দেখা হবে।
10. **বড় তালিকায় keyset pagination**, offset নয়।
11. **`events` টেবিল মাসভিত্তিক partition** (`pg_partman` থাকলে সেটা দিয়ে, নইলে pg_cron দিয়ে প্রতি মাসে নতুন partition)। পুরনো খুঁটিনাটি ইভেন্ট সারসংক্ষেপ করে আর্কাইভ।
12. **View হবে `security_invoker`।** `anon` রোলের grant ন্যূনতম।

## ৭. অ্যাপ কোডের নিয়ম

1. **ফিচার-মডিউল কাঠামো:** প্রতিটা ফিচার নিজের ফোল্ডারে। এক ফিচার অন্য ফিচারের ভেতরের ফাইল সরাসরি import করবে না, শুধু `index.ts` দিয়ে — ESLint নিয়ম দিয়ে প্রয়োগ।
2. **ডেটাবেস কল শুধু `api.ts`-এ।** স্ক্রিন বা কম্পোনেন্ট সরাসরি Supabase ডাকবে না।
3. **`app/` ফোল্ডারের স্ক্রিন পাতলা:** শুধু feature-এর screen import করে export করবে।
4. **রেজিস্ট্রি প্যাটার্ন:** ট্যাব, মেনু, content রেন্ডারার, ড্যাশবোর্ড উইজেট, অ্যাক্সেস রুলের UI — সব রেজিস্ট্রিতে; পারমিশন আর ফিচার ফ্ল্যাগ দেখে ফিল্টার। নতুন কিছু যোগ করতে পুরনো স্ক্রিনে হাত দিতে হবে না।
5. **ডিজাইন সিস্টেম:** সব বেসিক কম্পোনেন্ট `ui/`-তে; রং, ফন্ট, spacing টোকেন এক জায়গায়।
6. **i18n প্রথম দিন থেকে:** কোডে কোনো লেখা সরাসরি থাকবে না; প্রতিটা নতুন key `bn.json` আর `en.json` দুটোতেই।
7. **গোপন key কখনো অ্যাপে নয়।** `EXPO_PUBLIC_` মানেই পাবলিক। গোপন key শুধু Edge Function secrets আর GitHub Secrets-এ।
8. **ক্লায়েন্টকে কখনো বিশ্বাস করা হবে না:** দাম, নম্বর, সময়, অনুমতি — সব সার্ভারে যাচাই।
9. **`any` নিষেধ;** বাইরের ডেটা (API, JSON config) zod দিয়ে parse করে তারপর ব্যবহার।
10. **কাঁচা HTML রেন্ডার নিষেধ;** rich text/markdown হলে sanitize।
11. **লগে গোপন তথ্য নয়:** টোকেন, OTP, ফোন নম্বর, পাসওয়ার্ড লগে বা Sentry-তে যাবে না।
12. **নেটিভ মডিউল আগেভাগে:** যেসব নেটিভ মডিউল পরে লাগবে (Notifee, PDF, ফন্ট, screen-capture), সম্ভব হলে আগের ফেজেই যোগ হবে, যাতে নতুন APK কম লাগে।

### ৯.৪ API ও Edge Function
- প্রতিটা Edge Function-এ JWT ও পারমিশন যাচাই; ইনপুট zod দিয়ে যাচাই।
- SSLCommerz IPN-এ Validation API দিয়ে পুনর্যাচাই; অন্য webhook-এ signature যাচাই।
- Edge Function আর RPC-তে rate limit; pagination-এর সর্বোচ্চ সীমা; অনুরোধের সাইজের সীমা।
- CORS: শুধু নিজের ডোমেইন।
- বাইরের লিংক (YouTube, রিসোর্স) allowlist-করা ডোমেইন থেকে কিনা যাচাই।

### ৯.৫ ওয়েব
- কাঁচা HTML নয়; rich text sanitize (DOMPurify বা অনুরূপ)।
- কঠোর Content Security Policy; থার্ড-পার্টি স্ক্রিপ্ট ন্যূনতম।
- `frame-ancestors` (clickjacking), HTTPS + HSTS।
- CSV/Excel এক্সপোর্টে `=`, `+`, `-`, `@` দিয়ে শুরু হওয়া ঘর নিরাপদ করা।

### ৯.৬ মোবাইল
- JS bundle পড়া সম্ভব ধরে নেওয়া হবে — কোনো গোপন তথ্য বা গোপন ব্যবসা-নিয়ম ক্লায়েন্টে নয়।
- `allowBackup: false`।
- পরীক্ষা ও পেমেন্ট স্ক্রিনে স্ক্রিনশট বন্ধ।
- ক্যামেরা/মাইক/স্টোরেজ পারমিশন শুধু দরকারের সময়, কারণ ব্যাখ্যা করে।
- ঐচ্ছিক (ফেজ ১৪): পরীক্ষার জন্য Play Integrity API।

### ৯.৭ ফাইল আপলোড
- টাইপ ও সাইজ ক্লায়েন্ট আর storage policy — দুই জায়গায় যাচাই; ফাইলের নাম sanitize; প্রতি ব্যবহারকারীর কোটা।
- আপলোডের আগে ছবির **EXIF/GPS মেটাডেটা মুছে ফেলা** (শিশুদের সুরক্ষা)।
- private bucket আর স্বল্পমেয়াদি signed URL।

### ৯.৮ শিশু সুরক্ষা, অপব্যবহার ও অপারেশন
- মেসেজিং শুধু অনুমোদিত সম্পর্কে (শিক্ষক↔নিজের গ্রুপের শিক্ষার্থী, অভিভাবক↔শিক্ষক); শিক্ষক-শিক্ষার্থীর কথোপকথন অভিভাবক আর কোঅর্ডিনেটর দেখতে পারবেন; অপরিচিতের সাথে DM নেই।
- Report আর Block বাটন, মডারেশন কিউ, শব্দ-ফিল্টার, rate limit।
- কুপন/ট্রায়াল: প্রতি ব্যবহারকারী/ডিভাইসে সীমা, মেয়াদ, মোট সীমা।
- সাপ্লাই চেইন: lockfile কমিট; Dependabot; CI-তে `npm audit`; GitHub Action-গুলো commit SHA-তে pin; ন্যূনতম পারমিশনের টোকেন; secret scanning + push protection।
- সব সার্ভিস অ্যাকাউন্টে (Supabase, GitHub, Expo, SSLCommerz, BulkSMSBD, হোস্টিং) 2FA; প্রোডাকশনের key শুধু দরকারি লোকের কাছে; key rotation প্রক্রিয়া লেখা থাকবে।
- সন্দেহজনক কার্যকলাপে অ্যালার্ট: অনেক ব্যর্থ লগইন, হঠাৎ বেশি ডেটা এক্সপোর্ট, অ্যাডমিনের ভূমিকা বদল।
- ডেটা গোপনীয়তা: ন্যূনতম ডেটা সংগ্রহ; retention নিয়ম; ব্যবহারকারী নিজের ডেটা এক্সপোর্ট করতে পারবে।

### ৯.৯ লঞ্চের আগে নিরাপত্তা যাচাই (ফেজ ১৪)

- নিরাপত্তার E2E টেস্ট পাস: অন্য স্কুলের ডেটা দেখার চেষ্টা, পরীক্ষার উত্তর আগে পাওয়ার চেষ্টা, পেমেন্টের পরিমাণ বদলানোর চেষ্টা।

### ১০.১ Play Store-এর পেমেন্ট নীতি (D9 — গুরুত্বপূর্ণ ঝুঁকি)
Google Play-এর নীতি অনুযায়ী অ্যাপের ভেতরে ডিজিটাল কনটেন্ট (কোর্স, সাবস্ক্রিপশন) বিক্রিতে সাধারণত Google Play Billing লাগে; iOS-এ নিয়ম আরও কড়া। SSLCommerz/bKash দিয়ে অ্যাপের ভেতরে কোর্স বিক্রি করলে রিজেক্টের ঝুঁকি আছে।
- **ফেজ ৭-এর আগে** Play-এর তখনকার নীতি যাচাই করে সিদ্ধান্ত `decisions-log`-এ লেখা হবে।
- সম্ভাব্য পথ: প্রতিষ্ঠানের SaaS সাবস্ক্রিপশন ইনভয়েসে (অ্যাপের বাইরে); একক কেনাকাটা ওয়েবে; অথবা Play Billing।
- প্রোডাক্ট ইঞ্জিন **চ্যানেল-নিরপেক্ষ** হবে: `payments.channel` (sslcommerz/play_billing/invoice/manual)। চ্যানেল বদলালে enrollment বা লেজারের কোড বদলাবে না।

### ১০.২ নিয়ম
| বিষয় | কী করা হবে |
|---|---|
| টাকা integer | সব টাকা পয়সায় (৳১২০.৫০ = 12050) |
| দাম সার্ভারে | ক্লায়েন্ট থেকে আসা দাম কখনো বিশ্বাস করা হবে না |
| IPN যাচাই | SSLCommerz Validation API দিয়ে আবার যাচাই; অ্যাপ থেকে আসা "সফল" বার্তা বিশ্বাস নয় |
| Idempotency | `tran_id` unique; IPN রিট্রাই বা ডাবল ক্লিকে ডাবল enrollment হবে না |
| Transaction | পেমেন্ট → enrollment → ইনভয়েস এক ডেটাবেস ফাংশনে (সব বা কিছুই না) |
| লেজার | নির্মাতার আয়, রিফান্ড, উত্তোলন `ledger_entries`-এ শুধু নতুন এন্ট্রি; ব্যালেন্স = এন্ট্রির যোগফল |
| রিকনসিলিয়েশন | প্রতিদিন cron দিয়ে গেটওয়ের রেকর্ড আর নিজের ডেটাবেস মেলানো; অমিলে অ্যালার্ট |

## ১২. বিল্ড, রিলিজ ও মনিটরিং

### ১২.১ তিন ধরনের বিল্ড
| পদ্ধতি | কখন | কী হয় |

| **EAS ক্লাউড বিল্ড** | টেস্টারদের APK, Play Store-এর AAB | Expo-র সার্ভারে |
| **লোকাল (Android Studio)** | ডিবাগ বা জরুরি দরকারে | নিজের কম্পিউটারে |

### ১২.২ eas.json প্রোফাইল
- `development`: development client
- `preview`: APK, চ্যানেল `preview` (`dev` ব্রাঞ্চ থেকে, টেস্টারদের জন্য)
- `production`: AAB, চ্যানেল `production` (`main` থেকে)

### ১২.৩ GitHub Actions
- `ci.yml`: প্রতিটা PR-এ typecheck, lint, unit test, pgTAP (লোকাল Supabase), টাইপ জেনারেশন মিলিয়ে দেখা, `bn.json` আর `en.json`-এর key মিলছে কিনা, হার্ডকোড রং আছে কিনা (lint), `npm audit`
- `eas-update.yml`: push হলে `eas update --channel <preview|production>`
- `eas-build.yml`: হাতে চালানো (workflow_dispatch) বা version tag দিলে বিল্ড; EAS কোটা শেষ হলে runner-এ `eas build --local`
- Secrets: `EXPO_TOKEN` ইত্যাদি GitHub Secrets-এ; পাবলিক Supabase URL/key EAS environment variables-এ
- প্রোডাকশন migration শুধু CI দিয়ে, হাতে নয়

### ১২.৪ OTA যেন অ্যাপ না ভাঙে
- `runtimeVersion` পলিসি `fingerprint`: নেটিভ বদলালে runtime নিজে বদলায়, পুরনো APK-তে ভুল আপডেট যায় না।
- নতুন নেটিভ মডিউল → নতুন বিল্ড। শুধু স্ক্রিন/লজিক/টেক্সট → EAS Update।
- খারাপ আপডেটে rollback প্রক্রিয়া `docs/runbooks/`-এ লেখা থাকবে।

### ১২.৫ ফেরত আসার ব্যবস্থা
- **Force update:** `app_versions`-এ সর্বনিম্ন ভার্সন; পুরনো অ্যাপে "আপডেট করুন" স্ক্রিন। (contract ধাপের আগে এটা ব্যবহার হবে)
- **Kill switch:** ফিচার ফ্ল্যাগে তাৎক্ষণিক বন্ধ।
- **Staged rollout:** Play Store-এ ১০% → সবাই; আগে `preview` চ্যানেলে টেস্টার।
- **ব্যাকআপ:** দৈনিক ব্যাকআপ, প্রোডাকশনে PITR (পেইড); লঞ্চের আগে একবার রিস্টোর অনুশীলন।
- **পরিবেশ:** dev → staging → prod।
